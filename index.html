The problem

AI coding agents write code fast. They do not know the business rules of a marketplace: which listing fields a dealer must fill, which prices the page can show, which SEO rules apply. A fast agent with no rules gives fast code that breaks a rule in a quiet way. A reviewer then finds the problem late, or a user finds it in production.

So the question for the team was not "Which model do we use?" It was "What must the agent know before it starts, and what must it pass before it merges?"

The workflow

Each feature goes through the same 6 steps. The first 5 are commands from an open-source skills workflow. My plugins add the business-rule check at the start, and the gates around each step. The agent does the slow, repeated work. A person owns each decision.

  1. Grill the request /grill-with-docsAgent, then personBefore the first question, the agent loads every domain skill for the repo and checks the PRD against its business rules. Then it asks the engineer questions until the plan has no gaps.
  2. Write the spec /to-specPerson approvesThe spec is a GitHub issue. A new or changed business rule goes in as a decision, with the link to its rule update.
  3. Cut the tickets /to-ticketsAgentThin slices, end to end, into Jira. A slice with more than 15 files or 400 lines of code is split, so that a person can read each pull request.
  4. Build each ticket /implementAgentTest first, 1 ticket at a time. Or all ready tickets in parallel, on 1 integration branch.
  5. Review the code /code-reviewAgent2 checks: the team coding standards, and the spec. Findings go back to step 4. Then a browser test writes a report with screenshots and API calls.
  6. Review and mergePersonNo pull request merges without a human approval.

When the grill finds a gap

A business rule is something that a product page must always do. Code that breaks a rule is a bug. The rules live in domain skills, 1 plugin for each product, each rule with its reason.

A hook starts each time an engineer runs the grill. Before the first question, the agent compares the request with the rules and reports 1 of 4 results:

No skill covers the area
This is a domain gap. The agent searches for an open domain-gap issue. If there is none, it asks the engineer, then creates the GitHub issue and assigns it to that engineer. The feature work continues: the agent reads the code for that area and says that no rules cover it. Later, the same engineer turns the issue into a new domain skill.
A rule changes, or a rule is missing
The agent says so first. The engineer updates the domain skill in a pull request, then the grill continues. The spec quotes the new rule with that link.
The A/B test setup is not clear
The agent asks in its first round. It never guesses which users are in which group.
No rule is touched
The agent says so, and the grill continues. Most style changes end here.

This is the command that the hook gives the agent for a gap:

# is there an open gap issue for this area?
gh issue list --label domain-gap --state open --search "<area>"

# none: create it, and assign it to the engineer who runs the grill
gh issue create --label domain-gap --assignee @me \
  --title "<repo>: no skill for <area>" --body "<the request>"

The result: the rules grow from real feature work, not from a separate project. Each gap has an owner from the first day, and no rule lives only in 1 person's head.

The tools behind it

I designed a Claude Code plugin marketplace for the frontend teams: 7 plugins with 18 skills, in 5 product repos. A shared plugin holds the team standards. Domain plugins hold the business rules of each product. The plugins extend an open-source skills workflow.

A plugin ships only if it makes the output better

Each plugin release goes through 3 gates:

  • A CI check on each pull request.
  • A version and a change log through Changesets, so each team knows what changed.
  • An eval suite that runs the same tasks with and without the plugin. If the result with the plugin is not better, the plugin does not ship.

The 1 revert

Release r54, 7 October 2026. I upgraded all packages in 1 pull request to close 96 Dependabot alerts. I wrote that change by hand, outside the AI workflow. We undid it the next day, in release r55.

The lesson: a large change that skips the small steps is a risk, if a person or an agent writes it.

What I learned

A better model does not fix a bad spec

Most bad AI output came from a vague input. The largest gain came from the business-rule check before the spec, not from a newer model.

Measure the result, not the volume

The number of lines that AI writes says nothing about quality. The revert rate and the release pace do. These are the numbers that I track.

The engineer's job changes

Engineers write less code by hand. They own more of the requirements, the gates, and the final approval.
